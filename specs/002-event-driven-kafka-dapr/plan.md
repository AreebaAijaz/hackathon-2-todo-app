# Implementation Plan: Phase 5B - Event-Driven Architecture with Kafka & Dapr

**Branch**: `002-event-driven-kafka-dapr` | **Date**: 2026-02-08 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/002-event-driven-kafka-dapr/spec.md`

## Summary

Transform the existing TaskFlow todo application into an event-driven microservices system. The backend publishes domain events (task.created, task.updated, task.completed, task.deleted) to Kafka topics via Dapr pub/sub. Three new microservices consume these events: a recurring task service (auto-creates next task on completion), a notification service (logs reminders before due dates), and an audit service (persists all task events). All infrastructure runs on the local Minikube cluster using Redpanda (Kafka-compatible broker) and Dapr for infrastructure abstraction.

## Technical Context

**Language/Version**: Python 3.13 (matching existing backend)
**Primary Dependencies**: FastAPI, uvicorn, httpx (for Dapr HTTP API), SQLModel (backend only)
**Storage**: PostgreSQL (Neon - existing), Redpanda (Kafka-compatible message broker)
**Testing**: Manual integration testing via curl + Kafka CLI + pod logs
**Target Platform**: Kubernetes (Minikube) with Docker driver on Windows
**Project Type**: Microservices (web backend + 3 event-driven services)
**Performance Goals**: Events published within 2s of mutation, recurring task created within 5s
**Constraints**: Local Minikube only, fire-and-forget publishing, console-only notifications
**Scale/Scope**: Single-node Redpanda, 1 replica per service, single developer

## Implementation Phases

### Phase 1: Infrastructure Setup (Dapr + Redpanda)

**Goal**: Dapr runtime and Redpanda broker running on Minikube with topics created.

**Tasks**:
1. Initialize Dapr on Minikube (`dapr init -k`)
2. Create Redpanda K8s manifests (StatefulSet + Service)
3. Deploy Redpanda and create 3 Kafka topics
4. Create Dapr kafka-pubsub component YAML
5. Deploy Dapr component and verify

**Checkpoint**: `dapr status -k` shows healthy, `rpk topic list` shows 3 topics.

### Phase 2: Backend Event Publishing

**Goal**: All task mutations publish events to Kafka via Dapr.

**Tasks**:
1. Create `backend/events/schemas.py` with TaskEvent and ReminderEvent models
2. Create `backend/events/publisher.py` with `publish_event()` helper
3. Add `parent_task_id` field to Task model + Alembic migration
4. Update `backend/routes/tasks.py` to publish events after create/update/complete/delete
5. Update `backend/mcp_server/tools.py` to publish events after MCP mutations
6. Add `httpx` dependency if not present
7. Add `DAPR_HTTP_PORT` env var support with graceful fallback
8. Rebuild backend Docker image as v4

**Checkpoint**: Create a task via curl, verify event in `task-events` topic via `rpk topic consume`.

### Phase 3: Recurring Task Service

**Goal**: Completing a recurring task auto-creates the next instance.

**Tasks**:
1. Create `services/recurring-service/` project (main.py, Dockerfile, pyproject.toml)
2. Implement `/health` endpoint
3. Implement `/task-events` handler that filters for `task.completed` events
4. Implement next-occurrence date calculation (daily/weekly/monthly)
5. Implement idempotent task creation via Dapr service invocation to backend
6. Build Docker image
7. Create Helm chart templates (deployment + service)
8. Create Dapr subscription YAML
9. Deploy and test

**Checkpoint**: Complete a daily recurring task, verify new task appears with +1 day due date.

### Phase 4: Notification Service

**Goal**: Reminders logged to console for tasks approaching due dates.

## Complexity Tracking

| Concern | Decision | Why Simple Alternative is Insufficient |
|---------|----------|---------------------------------------|
| 3 new microservices | Separate services per domain | Monolith can't demonstrate event-driven architecture; services are minimal (~100 LOC each) |
| Kafka broker | Redpanda single-node | Simpler than Apache Kafka (no Zookeeper), still Kafka-compatible |
| Dapr infrastructure | CLI-based install | Simplest way to get pub/sub, service invocation, secrets on K8s |
| Fire-and-forget publishing | No retry/DLQ | Acceptable for local dev; keeps backend simple and non-blocking |

## Risks

1. **Minikube resource pressure**: 4 application pods + Redpanda + Dapr control plane + sidecars could strain a 4GB Minikube. Mitigation: Recommend 6GB+ memory, monitor pod evictions.
2. **Dapr sidecar injection timing**: Sidecar must be ready before app starts publishing. Mitigation: Dapr init containers handle this automatically.
3. **Service-to-service auth**: Recurring service needs to create tasks on behalf of users. Mitigation: Use Dapr service invocation headers for internal trust.
